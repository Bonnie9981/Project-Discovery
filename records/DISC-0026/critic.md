## 攻擊項目

1. **定義對不對（條目原文）。** A372430 %C：二進位指標是「反轉後二進位展開中 1 的位置」，從 1 開始算（A048793）；質數指標 m 指 prime(m) | k。猜想方向是「二進位指標 ⊆ 質數指標」，跟條目本身的數列方向相反，紀錄沒有搞混。我用 `bin(k)[2:][::-1]` 從頭重寫：4100 的二進位指標是 {3, 13}，因數分解 [2,2,5,5,41]，跟條目講的一致，所以「從 1 開始」的讀法跟作者相同。
   結果：k = 2^87 + 2^49 的二進位指標是 {50, 88}；試除法得到 2^38 + 1 = 5 · 229 · 457 · 525313；prime(50) = 229、prime(88) = 457（自己生成質數表），所以 k 符合條件。**反例成立。**

2. **DFS 是不是真的窮舉（`a372430_dfs.c`）。**
   - 邏輯：dfs(r, v, M) 代表第 L..r+1 位已經定好，k 落在 [v·2^r, v·2^r + 2^r)。把第 r 位設成 1 時，乘上 P[r]（也就是第 r−1 個位元，指標 r），對應關係正確。M 是不同質數的乘積，等於它們的 lcm，所以「M | k」對任何解都是必要條件；葉節點從第一個 ≥ lo 的 M 倍數開始列，再用 `full_ok` 檢查所有位元。r = 0 時 span/M = 0 < 8，一定會停。任何解都在它自己的位元路徑上被列出來，**沒有漏**。
   - 最高位：dfs(L−1, 1, P[L]) 把第 L 位固定成 1，模數 P[L]，等於 prime(L) | k，正確。L 從 1 跑到 LMAX；P 算了 LMAX+1 個質數，陣列大小 200，夠用。
   - u128 溢位：只在 span/M ≥ 8 時才往下分支，所以乘之前 M ≤ 2^(r−3) ≤ 2^116，P[r] ≤ 659 < 2^10，乘完 < 2^126；lo + span ≤ 2^120。**不會溢位。**
   - **變異測試（實際跑過）：** 把 P 換成「大多是 1、另外六個位置放不同質數」，LMAX = 22，DFS 跟 Python 暴力法逐一比對 k < 2^22：兩邊都是 149447 個解，清單完全相同。另外試過把模數換成互相不互質的數（j mod 4 + 2）：結果不一致（9413 對 83321），原因是乘積不再等於 lcm。用質數不會發生這種情況，所以不影響原程式；但這也說明：這個剪枝只在模數兩兩互質時成立。
   - 門檻敏感度：門檻從 8 改成 1 和 64，LMAX = 90 都只輸出 4100 和反例（節點數 9148 萬、2854 萬）。原程式 LMAX = 100：2.65 億個節點，7.7 秒，2 個解，跟 experiment.md 對得上。完整的 2^120 那次（3 分 20 秒）超過我的時間上限，**沒有重跑**。

3. **Lean 敘述（`lean/Discovery/A372430Counter.lean`）。**
   - `isPrimeB` 試除 2..n−1（`List.range (n-2)` 加 2），而且有 `isPrimeB_iff` 證明它等於一般的質數定義。`IsPrime p ∧ primesBelow p = j−1` 剛好就是「p 是第 j 個質數」：229 → 49 → 第 50 個；457 → 87 → 第 88 個。
   - `testBit i` 對應二進位指標 i+1：49 → 50、87 → 88，跟 prime(50) = 229、prime(88) = 457 對得上，沒有差一。
   - 檔案有被 `lean/Discovery.lean` 第 26 行 import，CI 確實會編譯它，也會做 axiom 檢查。
   - 小缺點（不必修）：總定理只說「i < 88 的 1 位元都在 {49, 87} 裡」加上 k < 2^88，沒有直接寫出「i ≥ 88 時 testBit 是 false」，要讀者自己補上 k < 2^88 ⇒ 高位是 0 這個標準事實。另外也沒有把條件寫成一句封閉的「∀ i, testBit k i → nthPrime(i+1) ∣ k」。不過條件只要求「所有 1 位元」對應的質數整除 k，所以只要 1 位元 ⊆ {49, 87} 加上兩個整除就足夠，敘述是忠實的。本機沒有 Lean，CI 綠燈這點沒有重驗。

4. **A219433 掃描（`a219433_scan.c`）。**
   - 3-smooth 表：雙層迴圈列出所有 2^i·3^j < 2^40（大約 500 個，陣列給 4000），再用 qsort 排序。完整而且有排好序。
   - 溢位保護：用 (u128)p·a + 1 ≥ 2^64 判斷，碰到就停，印 NONE（不算進例外）。因為表是遞增的，從這裡停下是對的。
   - Miller–Rabin：用前 12 個質數（2..37）當底數，對 n < 3.18·10^23 是確定性的，涵蓋 2^64；乘法取模用 u128，正確。
   - PLIM = n(ln n + ln ln n) + 100 是 p_n 的上界（n ≥ 6 時成立）。n = 10^8 時 ≈ 2.133·10^9 > p_n = 2038074743。
   - 實際跑過：C 程式 n ≤ 10^7（48 秒）只輸出 n = 522720, p = 7728803, a = 12582912，跟條目一致。我另外用 Python 從頭寫一份（自己篩質數、自己寫 MR，3-smooth 數到 2^60），n ≤ 6·10^5：前 32 項跟 %S 完全相同，例外也只有 (522720, 7728803, 12582912)。n ≤ 10^8 那次（約 10 分鐘）超過我的時間上限，**沒有重跑**。
   - 記憶體：n = 10^8 時篩法陣列 calloc 了約 2.13·10^9 bytes ≈ 2034 MiB，貼著 `config/limits.json` 的 2048 MB 上限。這次沒超過，但再往上延伸就會超過，到時要回報 INCONCLUSIVE，不能自行調高上限。
