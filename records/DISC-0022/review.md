## 審查項目

**1. 剪枝論證（邊極小加相鄰對換字典序）：正確。**
- 邊極小：反例一直刪邊、刪到再刪就有點的度數掉到 3 以下為止。刪邊不會多出圈，點數也不變，所以刪完還是反例，而且每條邊都至少有一端度數恰好 3。編碼裡 `e(a,b) → d(a) ∨ d(b)` 和 `d(v) → v 的任四條邊不全有`，加上 DEG 子句，正好表達「每條邊至少一端度數 = 3」。`d` 只有單向，只會放寬，不會誤殺。
- 字典序：邊極小在重新標號後不變，所以可以在同構類裡挑上三角向量（按列優先、和變數編號同順序）字典序最大的標號，它對任何置換都不會變小，相鄰對換只是其中一部分。我逐行看過 `encode.lex` 和 `check.spec_clauses`：只比對換後真的會變的位置（沒變的位置本來就相等，跳過沒問題）；`前綴相等 → x ≥ y` 寫成 `[-prev, x, -y]`；輔助變數只寫「相等 → a」這個方向，也只是放寬。對換後的向量在位置 (a,b) 的值是 e(σa,σb)，因為 σ 是對合，方向沒有弄反。
- DEG：每個點 v、任兩個其他點 T，v 連到 T 以外的點至少一條邊，這就等於 deg(v) ≥ 3。
- 圈長：n ≤ 19 時 2 的次方只有 4、8、16。C4 全部列出；C8 和 C16 用 CEGAR 擋，C16 在 n ≥ 16 才擋，這是對的。
- 佐證：`tests/test_egsat.py` 在 n = 5–7 和 networkx 圖譜逐類比對；critic 在 n = 10–18 把 CNF 當黑箱，用約 950 張隨機圖測過語意（0 個不一致）。n ≤ 7 的比對不含無 C4 的圖，效力比較弱，這點文件已經老實寫了。

**2. check.py 的規格重建：可信，但有「同一作者」的共同風險。**
- check.py 沒有 import encode 或 search。它照規格重建基本子句，要求兩邊集合完全相等；CNF 裡其他的子句只能是全負字面、而且剛好是 K_n 裡一個長度 4、8、16 的簡單圈（檢查度數都是 2、點數 = 邊數、連通）。這樣多擋的子句一定是合法限制，CNF 不可滿足就推得出「沒有反例」。變數總數也有比對。
- 風險：spec 的 lex 部分和 encode 幾乎逐行相同，一個概念錯誤會兩邊一起錯。我人工核對了語意（見第 1 項），critic 也做了語意測試，目前沒發現問題。

**3. RUP 檢查器：沒找到會誤收的路徑。**
- 我逐行看了 `propagate`、`add`、`is_rup`。宣告衝突時，子句的每個字面都確實是假的；推單位時，子句確實只剩一個未賦值字面。監看字面偶爾失效只會讓它漏推（變嚴），不會多收。刪除只停用子句，已推出的單位保留。這些單位都是由原公式推出來的，所以仍然健全。不接受 RAT 步驟。
- critic 做過模糊測試（36198 次，0 次不健全）和竄改測試；測試檔也有竄改證書、塞進非圈子句會被擋下的測試。
- 小缺點（建議）：證明檔被截斷時，只要單位傳播已經矛盾仍會通過。這在數學上合法，但輸出訊息容易讓人以為整份證書都讀完了。
